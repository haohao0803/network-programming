# 2026-11-13 — haohao0803 发送窗口补充记录

本次在停止等待发送端基础上，提前实现 11-14 计划中的本人发送侧部分。使用 `feature/sender`，继续在同一个草稿 PR 中供组员审阅。

## 本人新增成果

- 支持配置 1–256 个分片的发送窗口，默认 1 保留停止等待基线。
- 使用有界环形缓存保存未确认报文，回退重传使用原始字节；额外保留一个已确认报文用于探测，缓存规模不随文件增长。
- 累计 ACK 可一次确认多个分片；超过已发送范围、落后于当前 base 的确认不改变状态。重复 ACK 可更新窗口，但不延长超时。
- 发送范围同时受本地上限与接收窗口约束，窗口缩小后重传也遵守新范围。
- 零窗口以重复 START 或已确认 DATA 探测，恢复通告后继续发送。连续无进展受同一预算限制，持续重复 ACK 不会无限延长等待。
- 传输末尾检查源文件长度；源文件变大、变小时不发送完成请求。传输期间仍需保持源文件不变，同长度内容修改不是本阶段承诺检测的范围。
- 成功输出增加窗口上限、最大在途数、探测次数，便于后续实验接入；当前 RTO 固定，自适应 RTO 与 cwnd 模块待 LPCAQ 提供后整合。

核心状态为 `[base, next)` 的未确认范围，缓存位索引为 `sequence % WINDOW_PACKETS`。只有新累计确认才能释放原位置；重传不回退 next，也不重新读取源文件。这些可作为本人汇报的关键实现。

## 验证结果

环境为 Windows / WSL 2 Ubuntu-24.04 的临时隔离网络，未改变 VPN 设置。严格 C11 编译、干净构建和 `make check` 通过。原始日志见 [窗口验证日志](2026-11-13-window-validation.txt)。

`tests/test_sender.py` 的 7 个方法与新增 `tests/test_sender_window.py` 的 8 个方法均通过。新增测试明确验证：

1. 对端必须收到整批数据才确认，以此证明多包实际在途；分别检查本地上限小、接收窗口小、配置上限 256 及窗口为 1。
2. 中间分片丢失后回退重传，缓存重组后哈希一致；窗口缩小后不重传超出新范围的分片。
3. 模拟乱序、重复、未来确认及陈旧零窗口通告，仍完成正确交付。
4. 初始零窗口和传输中零窗口均可探测恢复；永久零窗口、持续无进展 ACK、远端错误均在限定时间内失败。
5. 0 B、1 B、1024 B、1025 B、1 MiB、10 MiB 与模拟对端接收字节的 SHA-256 一致。
6. 无效窗口参数被拒绝；传输中源文件变大或变小时不进入 FIN 完成阶段。

暂停前测试发现：1025 B 文件只有 2 个分片，测试却要求观察到 4 个在途分片。恢复后将期望修正为 `min(发送上限, 接收窗口, 文件分片数)`，再验证通过；没有通过削减文件或禁用场景绕过失败。

这些是 sender 与测试模拟对端之间的证据，不代表 Clive 的接收缓存、实际文件落盘或跨机器实验已经通过。也不是 Linux netem 丢包性能测试；测试中的故障由模拟对端按规则注入。

## 复现与联调

```sh
make
sudo unshare --net sh -c 'ip link set lo up && make check'
# 正式 receiver 可用后，在接收端启动并监听 UDP 端口，再发送：
./build/rudp-send RECEIVER_IPV4 19090 input.bin 1000 5 4
```

RECEIVER_IPV4 替换为实际数字地址。正常网络的 Mac/Linux 可直接 `make check`；上述隔离方法需要 Linux 权限。

Clive 需确认 PROTOCOL.md 中接收窗口“序号跨度”的定义，以及重复 START 不截断、已确认 DATA 在零窗口时仍返回 ACK 的行为。随后提供接收端分支及命令，本人负责联调并核对实际落盘哈希。

LPCAQ 需提供计时/拥塞参数的 C 接口和单位；当前发送循环的 ACK 与超时位置已明确，后续接入 RTO、退避和 cwnd。尚未实现自适应参数计算，不将固定窗口版本称为完整拥塞控制。
